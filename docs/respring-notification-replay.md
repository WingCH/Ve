# Respring 通知重播修正

日期：2026-10-03。修正版本：2.2.3。狀態：**指定 vphone 的 respring 重播與通知更新驗證已通過；使用者裝置仍待安裝回歸。**

## 問題與原因

2.2.1／2.2.2 的去重條件把 `bulletinID`、`bulletinVersionID` 當成穩定識別碼。實際 respring 會重新生成這兩個 transport IDs，所以日期、app 與內容相同的已儲存通知仍被判斷成新通知。

在使用者指定的 `iOS-26.6.2`／RootHide guest，以獨立測試 App 發送並保留一條通知，再執行 respring。接收端的 Bark POST 由 2 次增加至 3 次，Ve 歷史亦由 2 條增加至 3 條。

重播前後原文均有 `"publisherBulletinID" : "ve-lab-retained"`，且 `date` 均為 `2026-10-03T21:21:08.876`，但兩個 transport IDs 改變 — [重播前記錄](/Users/wingchan/Project/Ve/packages/safe-mode-investigation-20261003/guest/replay-baseline-history.json)、[重播後記錄](/Users/wingchan/Project/Ve/packages/safe-mode-investigation-20261003/guest/replay-history-after-respring.json)。這直接證明原本的 ID 比對會漏擋該重播。

## 修正

優先使用兩邊歷史已保存的 `raw_bulletin_data.publisherBulletinID`，並繼續核對 app、原始日期、標題、副標題與內容。原文：`return [currentPublisher isEqualToString:existingPublisher];` — [NotificationIdentity.h，第 44 行](/Users/wingchan/Project/Ve/Utils/NotificationIdentity.h:44)。因此 transport IDs 重新生成不再造成重複轉發。

缺少 publisher ID 的舊記錄保留原本的 bulletin ID fallback。版本 ID 單獨改變不再算內容更新。新內容、新日期、不同 app 及不同 publisher request 仍可轉發，不刪除既有歷史。

## 驗證

測試環境：vphone `iOS-26.6.2`，iOS 26.6.2／23G90、RootHide、ElleKit 1.2-1、PreferenceLoader 2.2.8。所有 guest 操作固定使用 `/Users/wingchan/.vphone/machines/iOS-26.6.2/vphone.sock`，沒有操作 keyboard-test。Bark receiver 只綁定 host NAT interface，使用測試內容及 dummy key，並阻擋其他 app 的轉發。

| 情境 | 實際結果 |
|---|---|
| 原版 2.2.2 respring | POST 2 → 3，歷史 2 → 3，成功重現重複轉發 |
| 修正後 2.2.3 respring | POST 3 → 3，歷史 3 → 3，沒有新增重播 |
| 更新測試通知內容 | POST 3 → 4，歷史 3 → 4，最後 body 為 `notification-v2` |
| 更新內容後再次 respring | POST 4 → 4，歷史 4 → 4，沒有新增重播 |
| 指定 VM 關閉／啟動 | POST 4 → 4，歷史 4 → 4，沒有新增重播 |
| macOS Foundation 回歸 | 20 個 assertions 通過，包含另一個 process 讀回歷史 |

實際驗證原文：`"passed": true` — [第一次 respring](/Users/wingchan/Project/Ve/packages/safe-mode-investigation-20261003/guest/fixed-respring-result.json)、[內容更新](/Users/wingchan/Project/Ve/packages/safe-mode-investigation-20261003/guest/fixed-update-result.json)、[再次 respring](/Users/wingchan/Project/Ve/packages/safe-mode-investigation-20261003/guest/fixed-update-replay-result.json)。這些是 guest 上的實際 HTTP request 及 JSON 歷史數量，不是 mock 結果。

回歸測試在修正前顯示原文：`FAIL: suppress a retained notification whose transport IDs were regenerated by respring` — [失敗紀錄](/Users/wingchan/Project/Ve/packages/safe-mode-investigation-20261003/publisher-id-regression-before.log)。修正後原文：`20 assertions; history reloaded in a new process` — [通過紀錄](/Users/wingchan/Project/Ve/packages/safe-mode-investigation-20261003/publisher-id-regression-after.log)。

Rootless 與 RootHide 兩個 packages 均用 macOS／Xcode 原生建置。三個模組均通過 arm64e versioned ABI、全部 slices 的簽署，以及保存 dSYM 的 UUID 驗證。

Guest 的 userspace reboot RPC 回覆原文：`reboot request rejected: Input/output error` — [RPC 結果](/Users/wingchan/Project/Ve/packages/safe-mode-investigation-20261003/guest/fixed-userspace-reboot.json)。因此改以 Launchpad 對指定 VM 執行 stop／start，原文：`"passed": true` — [VM 重啟結果](/Users/wingchan/Project/Ve/packages/safe-mode-investigation-20261003/guest/fixed-cold-restart-result.json)。兩種 restart 方法的證據保持分開。

## 範圍

以上 runtime 結果限於指定 RootHide vphone，不能代替使用者的 rootless／Relaxin 真機回歸。2.2.3 沒有修改通知清除、history limit 或 Settings 的 iOS 26 相容性。

缺少穩定 publisher ID 的歷史維持保守 fallback；清除或被 log limit 移除的記錄仍無法作重播比對。這些條件未被本次修正放寬。
